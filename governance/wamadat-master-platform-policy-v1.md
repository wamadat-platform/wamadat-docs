## السياق

ومضات: عربيّة أولاً · سعوديّة أولاً · مؤسّسة واحدة · ليست SaaS · ليست سوقاً (marketplace) · ليست multi-tenant كمنتج تجاري · مُدارة مركزياً. الهدف: أوثق منصّة تعلّم وتدريب عربية في فئتها.

**يجب أن تشعر:** Premium · احترافية · بسيطة · محوكمة · موثوقة · إنسانية · سهلة.
**يجب ألّا تشعر:** LMS عام · سوق · بوابة حكومية · موقع قالب · SaaS مفرط الهندسة.

## القسم ١ — كيانات المنصّة الرسمية (مقفّلة)

| الكيان | التعريف (ما هو) | ما هو **ليس** |
|---|---|---|
| **المسارات التعليمية** (Learning Paths) | رحلة مجمّعة تحتوي ٣–٦ برامج، تُشترى مرّة واحدة | ليست برنامجاً، ولا تصدر شهادة بنفسها |
| **البرامج التدريبية** (Training Programs) | تجربة تدريب عملية مستقلة (عادة ٣–٥ أيام)، قد تصدر شهادة | ليست درساً مفرداً ولا دورة فيديو فقط |
| **المختبرات التدريبية** (Training Labs) | تجربة تطبيقية قصيرة مكثّفة (عادة ١–٢ يوم) | ليست ورشة عامة عابرة |
| **المبادرات المجتمعية** (Community Initiatives) | نشاط مجتمعي مستقل، مجاني أو مدفوع، بتسجيل | ليست برنامجاً تجارياً بالضرورة |
| **الاستشارات** (Consultations) | طلب يُراجع ويُوافق عليه ثم يُدفع ويُجدول | ليست باقة شراء مباشر |
| **المدربون** (Trainers) | بطاقة شخص يدرّب (وقد يكون مستشاراً) | ليس مالكاً للمتدربين، ولا له صفحة عامة كاملة الآن |
| **فريق العمل** (Team Members) | أعضاء المنظّمة، يظهرون في "من نحن" فقط | ليسوا مدربين، ولا يظهرون في صفحة المدربين |
| **الشركاء** (Partners) | شعارات شركاء (عام أو مرتبط بكيان) | ليس لهم صفحات تفصيلية الآن |
| **المتدربون** (Learners) | المستخدم في دور التعلّم | ليسوا ملكاً لمدرّب؛ ينتمون لومضات |

## القسم ٢ — سياسة الحساب والهوية

- نموذج **مستخدم واحد** + **أدوار متعدّدة** (Roles). لا حسابات منفصلة للمدرب/المستشار/الفريق/المتدرّب.
- يمكن للمستخدم حمل أكثر من دور.
- الأدوار: Super Admin · Admin · Finance Admin · Trainer · Consultant · Team Member · Learner.
- تسجيل الدخول: **البريد + كلمة مرور** أو **الجوال + كلمة مرور**. لا اسم مستخدم، لا رمز عضوية.
- **لا هوية وطنية إجبارية** عند التسجيل الأولي. لا صورة ملف إجبارية.
- يرى المستخدم: الاسم · البريد · الجوال · الملف.
- يُسند النظام: **مرجع تجاري** (مثل `WMT-U-26-0001`) — يظهر في الملف وسياقات الدعم فقط، ولا يُطلب من المستخدم حفظه.

## القسم ٣ — سياسة المرجع التجاري (Business Reference)

- **مُعرّفات قاعدة البيانات لا تُكشف علناً أبداً.**
- لكل كائن أعمال **مرجع تجاري عام** يُولّد تلقائياً.
- الصيغة العامة: `WMT-TYPE-YYMM-0001` (تسلسل شهري حيث يناسب) أو `WMT-TYPE-YY-0001` (تسلسل سنوي للكيانات بطيئة الإنشاء).

| الكيان | الصيغة |
|---|---|
| مستخدم | `WMT-U-26-0001` |
| طلب استشارة | `WMT-C-2606-0001` |
| تسجيل (Enrollment) | `WMT-E-2606-0001` |
| دفعة | `WMT-PAY-2606-0001` |
| فاتورة | `WMT-INV-2606-0001` |
| شهادة | `WMT-CERT-2606-0001` |
| برنامج | `WMT-PRG-26-0001` |
| مسار | `WMT-PATH-26-0001` |
| مختبر | `WMT-LAB-26-0001` |
| مبادرة | `WMT-INIT-26-0001` |
| تذكرة دعم | `WMT-TKT-2606-0001` |

**القواعد:** يُولّد تلقائياً · لا يُعاد استخدامه · لا يُعدّل يدوياً · لا يُكشف كـ DB ID · يُعرض باتّساق للأدمن والمستخدم عند الحاجة.

**مبدأ Reality First:** المرجع التجاري يتبع كياناً **حقيقياً موجوداً** في النظام — لا نبني مرجعاً لكيان غير منمذج. *If there is no Model, there is no Business Reference.*

**حالة التنفيذ (2026-06-09):**

| النوع | الكيان | الحالة |
|---|---|---|
| `WMT-U` | المستخدمون | ✅ مُنفّذ (backfill 230، تسلسلي، لا تكرار) |
| `WMT-E` | التسجيلات | ✅ مُنفّذ (85) |
| `WMT-PAY` | الطلبات/الدفعات | ✅ مُنفّذ (4) |
| `WMT-INV` | الفواتير | ✅ مُنفّذ (9) |
| `WMT-CERT` | الشهادات المُصدرة | ✅ مُنفّذ (العمود+hook جاهزان؛ 0 سجلّ بعد؛ المرجع ثابت بعد الإصدار §14) |
| `WMT-PRG` | البرامج | ✅ مُنفّذ (30، صيغة سنوية) |
| `WMT-PATH` | المسارات | ✅ **مُنمذج (B1)** — جدول `learning_paths`؛ المرجع يُولّد؛ لا شهادة للمسار (§10). UI/أدمن عام لاحقاً. |
| `WMT-LAB` | المختبرات | ✅ **مُنمذج (B1)** — `programs.type='lab'` → `WMT-LAB`؛ يرث بنية البرنامج كاملة. |
| `WMT-INIT` | المبادرات | ✅ **مُنمذج (B1)** — `programs.type='initiative'` → `WMT-INIT`. |
| `WMT-TKT` | تذاكر الدعم | 🔒 **Reserved. Not Implemented. Awaiting Entity Creation.** (تذاكر الدعم ليست أولوية منتج حالياً) |

> **B1 Entity Modeling تمّ (2026-06-09):** المسارات كيان منفصل (`learning_paths`)، والمختبر/المبادرة نوعان على جدول `programs` المشترك (حقل `type` كان موجوداً أصلاً من `2026_05_15_160000`). الـ٣٠ برنامج الحالية = `type=program`. متبقٍّ من B1 (مراحل لاحقة): واجهة عامة + موارد أدمن + بوّابات الجودة §40 لكل نوع. يبقى `WMT-TKT` وحده محجوزاً (لا Model، وليس أولوية).

## القسم ٤ — سياسة التتبّع

كل عملية أعمال يجب أن تملك: مرجع تجاري · مالك · حالة · خط زمني · سجل تدقيق · ظهور للأدمن · ظهور للمستخدم عند الصلة.
- كيان ثابت لا يحتاج دائماً صفحة تتبّع عامة. العملية ذات المراحل تحتاج تتبّعاً.
- **تتبّع عام مطلوب لـ:** طلبات الاستشارة · طلبات التسجيل · طلبات الشهادة · تذاكر الدعم.
- **تتبّع الدفع** يظهر داخل لوحة المستخدم، لا كصفحة عامة.
- الأدمن يرى الخط الزمني الكامل؛ المستخدم يرى خطاً مبسّطاً: «تم استلام الطلب · قيد المراجعة · تمت الموافقة · مكتمل». الحالات الداخلية تبقى مخفية عند الحاجة.

## القسم ٥ — سياسة سجل التدقيق (Audit Log)

- سجلّات التدقيق **دائمة، لا تُحذف أبداً**. لا أحد فوق السجل — حتى Super Admin تُسجّل أفعاله.
- **يُسجَّل:** الدخول · الخروج · إنشاء حساب · تغيير كلمة المرور · تغيير البريد · تغيير الجوال · تغييرات الأدوار · تغييرات الصلاحيات · تغييرات الحالة · إصدار الشهادة · سحب الشهادة · تأكيد الدفع · الاسترداد · تغييرات الحضور · اعتماد الإكمال · إنشاء/تحديث/أرشفة البرنامج · موافقة/رفض الاستشارة · انتحال الأدمن (impersonation) · الوصول للملفات الحساسة · تصدير البيانات.
- كل سجل يتضمّن: الفاعل · الدور · الفعل · الكيان · القيمة القديمة · القيمة الجديدة · الطابع الزمني · السبب عند الصلة · الـ IP عند توفّره.

## القسم ٦ — سياسة الخصوصية والوصول الداخلي

**أقلّ صلاحية ممكنة (Least Privilege).** كل دور يرى ما يحتاجه فقط.
- **المتدرّب:** لا يرى متدربين آخرين ولا بياناتهم.
- **المدرّب:** يرى متدربي برامجه/مختبراته/مساراته/مبادراته المسندة فقط (الاسم/البريد/الجوال + التسليمات/الحضور/التقدّم/الإكمال). يرفع مواد، يصحّح، يعتمد حضوراً، يوصي بالإكمال. **لا يرى:** الدفعات · الفواتير · الإيرادات · الخصومات · الاستردادات · التقارير المالية · متدربي غيره · استشارات غير مسندة له · سجلّات التدقيق العامة.
- **المستشار:** يرى طلبات الاستشارة المسندة له فقط ومعلومات عميلها فقط. لا يرى الدفعات إلا بإذن صريح.
- **Finance Admin:** يرى الدفعات/الفواتير/الاستردادات/التقارير المالية. لا يغيّر مخرجات تعليمية إلا بدور إضافي.
- **Admin:** يدير حسب الصلاحيات؛ كل أفعاله مُدقّقة.
- **Super Admin:** يرى ويدير كل شيء؛ كل أفعاله مُدقّقة.

## القسم ٧ — سياسة الجدار المالي (Financial Firewall)

- البيانات المالية **معزولة** عن العمليات التعليمية. يراها فقط: Super Admin · Finance Admin · Admin مُخوّل.
- **المدرّب لا يرى أي تفصيل مالي** (حالة الدفع/المبلغ/الخصومات/الفواتير/بوّابات الدفع: Tamara/Tabby/Tap/Apple Pay/Visa/Mastercard/التحويل البنكي). يرى فقط: **«التسجيل مؤكّد / غير مؤكّد»**.
- **مبدأ الأربع أعين (Four-Eyes):** الأفعال المالية الحسّاسة تتطلّب طلب Admin + موافقة Super Admin. يشمل: الاسترداد · تأكيد الدفع اليدوي · إلغاء الفاتورة · تعديل مبلغ الدفع · تجاوز الخصم.

## القسم ٨ — سياسة الدفع

- الطرق المدعومة: التحويل البنكي · Tap · Apple Pay · Visa · Mastercard · Tabby · Tamara.
- لكل دفعة: مرجع دفع · مستخدم · تسجيل/استشارة مرتبطة · مبلغ · عملة · طريقة · حالة · فاتورة · خط زمني · سجل تدقيق.
- التحويل البنكي يتطلّب تأكيد الأدمن. الدفع الإلكتروني يتطلّب تأكيد البوّابة أو تجاوزاً يدوياً مُخوّلاً.
- **لا دفعات يتيمة (orphan):** كل دفعة ترتبط بمستخدم + عملية أعمال + فاتورة + سجل تدقيق.

## القسم ٩ — سياسة الاستشارات

- الاستشارات ليست باقات شراء مباشر. التدفّق الصحيح: طلب → مراجعة → موافقة → دفع → Calendly → جلسة → إكمال.
- **MVP الحالي يدعم:** طلب · رقم تتبّع · تحديث حالة الأدمن · صفحة تتبّع · ملاحظات داخلية.
- **مراحل لاحقة:** الدفع · Calendly · تعيين المستشار · الإشعارات.
- حالات MVP: New · Under Review · Approved · Rejected · Completed. المستخدم يرى لغة بسيطة لا مصطلحات داخلية.

## القسم ١٠ — سياسة المسار التعليمي

- المسار يحتوي ٣–٦ برامج، بدفعة واحدة. **لا يصدر شهادة**؛ كل برنامج داخله يصدر شهادته.
- البرنامج ينتمي لمسار واحد فقط؛ لو لزم نفس البرنامج في مسار آخر → يُنشأ سجل برنامج جديد.
- يفتح المستخدم كل برنامج مُضمّن ليفهم المحتوى.
- يعرض المسار: العنوان · الوصف · البرامج المضمّنة · المدة · المدربون · السعر · الحالة · توفّر التسجيل · المخرجات.

## القسم ١١ — سياسة البرنامج التدريبي

- عادة ٣–٥ أيام، عملي. مستقل أو ضمن مسار واحد. قد يملك عدّة مدربين ويصدر شهادة.
- قد يتضمّن: مواد · واجبات · حضور · قواعد إكمال · مراجعات · وسائط · معرض.
- البرامج المنتهية تبقى ظاهرة. الحالة تُعرض بوضوح: Open Registration · Coming Soon · Full · Completed.

## القسم ١٢ — سياسة المختبر التدريبي

- تجربة تطبيقية قصيرة (١–٢ يوم)، تُقدّم كمختبر تطبيقي لا ورشة عامة. قد يملك مدربين/مواد/واجبات/شهادة (إن فُعّلت)، مجاني أو مدفوع.

## القسم ١٣ — سياسة المبادرة المجتمعية

- مستقلة، مجانية أو مدفوعة، قد تصدر شهادة أو لا، بتسجيل. قد تملك شركاء/مدربين/تغطية إعلامية، وتبقى ظاهرة بعد الانتهاء.

## القسم ١٤ — سياسة الشهادات

- الشهادات تصدر **للبرامج لا للمسارات**. الإصدار يتطلّب: موافقة المدرب + اعتماد الأدمن النهائي (للأدمن تجاوز المدرب عند التبرير).
- متطلّبات قابلة للتهيئة لكل برنامج: حضور · موافقة مدرب · إكمال واجبات · نتيجة تقييم · قواعد هجينة.
- **بعد الإصدار:** نفس المرجع/الرقم يبقى للأبد، ولا تتغيّر الشهادة تلقائياً لو تغيّرت بيانات البرنامج لاحقاً. عند الخطأ: **سحب ثم إعادة إصدار** — لا تعديل صامت.
- تربط الشهادة بـ: مستخدم · برنامج · تسجيل · تاريخ إصدار · معتمِد · مرجع تحقّق. التحقق متاح من الفوتر.

## القسم ١٥ — سياسة الحضور

- يُسجَّل بـ: رمز حضور · تعليم يدوي من المدرب · تجاوز الأدمن. الأدمن هو المرجع النهائي (يضبط/يحذف الرمز).
- يتضمّن السجل: مستخدم · برنامج/مختبر · تاريخ · طريقة · المُسجِّل · طابع زمني · ملاحظات.
- الحضور قد يدعم أهليّة الشهادة لكنه ليس إلزامياً دائماً.

## القسم ١٦ — سياسة الإكمال والتقييم

- **لا نموذج نجاح/رسوب عام.** كل برنامج يعرّف طريقة إكماله من الأدمن: قائم على الحضور · موافقة المدرب · قائم على الواجبات · قائم على التقييم · هجين.
- النتيجة الافتراضية: **Completed / Not Completed**. النجاح/الرسوب يظهر فقط عند تفعيله للبرنامج.
- التقييمات/بنوك الأسئلة/الواجبات/المشاريع كلها اختيارية. أهليّة الشهادة تتبع قواعد البرنامج المهيّأة.

## القسم ١٧ — سياسة الملفات والوسائط

- لكل ملف: مالك · رافع · كيان مرتبط · نوع · ظهور · طابع زمني · صلاحيات وصول.
- **المسموح:** الأدمن (كل الأنواع المعتمدة) · المدرب (مواد/واجبات/PDF/شرائح/صوت/فيديو/موارد) · المتدرّب (واجبات/دراسات حالة/مشاريع/تسجيلات صوت وفيديو).
- حدود مقترحة: صور 20MB · PDF 100MB · Office 100MB · صوت 200MB · فيديو 500MB. الفيديوهات الكبيرة عبر روابط خارجية (Drive/OneDrive/YouTube Unlisted/Vimeo) — **لا تُخزّن افتراضياً على خادم التطبيق**.
- لا ملفات يتيمة، ولا ملف عام افتراضياً.

## القسم ١٨ — سياسة المعرض وقصص النجاح

- المعرض **دليل أثر محكوم** لا أرشيف صور عشوائي. يُدار كلياً من الأدمن، ويرتبط بـ برنامج/مسار/مختبر/مبادرة/شريك/مدرب.
- التسمية العامة المفضّلة لاحقاً: **«قصص النجاح»** أو **«تجارب ومضات»**. يبني الثقة والإثبات لا الفوضى.

## القسم ١٩ — سياسة المدربين

- المدرب **بطاقة فقط** الآن (لا صفحة عامة كاملة). الحقول: صورة · اسم · تخصّص · نبذة · علم Trainer · علم Consultant · ظهور · ترتيب.
- يظهر في: برامج/مسارات/مختبرات/مبادرات/استشارات. قد يحمل أدواراً متعدّدة. **لا يملك متدربين — المتدربون لومضات.**

## القسم ٢٠ — سياسة فريق العمل

- منفصلون عن المدربين، يظهرون في **«من نحن» فقط**. الحقول: صورة · اسم · منصب · نبذة · ظهور · ترتيب. قد يكون العضو مستشاراً أو يحمل أدوار أدمن إن مُنحت.

## القسم ٢١ — سياسة الشركاء

- نوعان: **شريك عام** (في "من نحن"/الرئيسية/أقسام الشركاء) و**شريك مرتبط** (ببرنامج/مسار/مختبر/مبادرة/استشارة).
- شعارات فقط الآن، بلا صفحات تفصيل. الحقول: اسم · شعار · موقع · نوع · كيان مرتبط · ظهور · ترتيب · حالة. عند انتهاء الشراكة: **يُعلَّم غير نشط، لا يُحذف**.

## القسم ٢٢ — سياسة المراجعات والتقييمات

- يراجع المتدرّب: برنامج/مدرب/مختبر/مبادرة. **لا نشر تلقائي.**
- حالات الأدمن: Pending Review · Published · Hidden · Rejected. المستخدم يرى فقط: «تم استلام تقييمك، شكراً لك». Super Admin يعتمد/يخفي/يرفض.
- المراجعة تبقى مخزّنة حتى لو أُخفيت/رُفضت. **لا حذف نهائي.**

## القسم ٢٣ — سياسة المجتمع

- ميزة مستقبلية **خلف feature-flag**، الحالة الافتراضية **معطّلة**. قد تشمل لاحقاً: منشورات/تعليقات/ردود/مجموعات/نقاشات. تتطلّب أدوات إشراف.
- **الرسائل الخاصة لا يقرؤها الأدمن** إلا عند: بلاغ · تحقيق · سماح السياسة · سبب قانوني/سلامة.

## القسم ٢٤ — سياسة الإشعارات

- القنوات: إشعارات داخل المنصّة · بريد عند تفعيل المزوّد. **الحالة الحالية: المزوّد قد يكون mock — لا نعتمد على البريد حتى يُهيّأ.**
- كل تغيّر حالة مهم يُنشئ إشعاراً مستقبلاً (استشارة/تسجيل/تأكيد دفع/شهادة/مراجعة واجب/تحديث برنامج/تغيير جدول). الإشعارات لا تكشف تفاصيل مالية لأدوار غير مخوّلة.

## القسم ٢٥ — سياسة التسجيل والتحقق

- **تسجيل منخفض الاحتكاك:** ينشئ حساباً ويدخل ويستخدم المنصّة **بدون OTP جوال أو تحقق بريد إجباري** عند أول دخول.
- الحماية الحالية: Honeypot · Rate limit · Spam log. تحقّق البريد مؤجّل لين يجهز المزوّد. OTP الجوال مؤجّل ما لم يوجد مبرر أعمال قوي.
- **حساب موثّق مطلوب لاحقاً للأفعال الحسّاسة:** الشراء · الوصول للشهادات · التقديم كمدرّب · التقديم كمستشار · تغييرات الحساب الحسّاسة.

## القسم ٢٦ — سياسة مكافحة العبث

- **كل نموذج عام** يجب أن يملك: Honeypot · Rate limit · Spam log. ينطبق على: التسجيل · التواصل · طلبات الاستشارة · النشرة · أي نموذج عام مستقبلي.
- CAPTCHA مؤجّل ما لم يظهر عبث. OTP الجوال مؤجّل. تحقّق البريد مؤجّل لين يجهز المزوّد.

## القسم ٢٧ — سياسة نشر المحتوى

- المحتوى العام يتبع: **Draft → Review → Published → Archived**. ينطبق على: برامج/مسارات/مختبرات/مبادرات/صفحات/معرض/قصص نجاح/FAQ/أقسام الرئيسية.
- لا نشر مباشر بلا الحقول المطلوبة: عنوان · وصف · صورة عند الحاجة · حالة · ظهور · مالك · ترتيب · حقول SEO عند العموم.

## القسم ٢٨ — سياسة الحذف والأرشفة

- **لا حذف نهائي افتراضي** لأي سجل أعمال. تُستخدم: Draft · Inactive · Archived · Cancelled · Rejected · Hidden · Soft Delete.
- الحذف النهائي: **Super Admin فقط** + سبب + تدقيق.
- **لا تُحذف نهائياً أبداً:** الشهادات · الدفعات · الفواتير · سجلّات التدقيق · التسجيلات · الحضور · طلبات الاستشارة · الشهادات المُصدرة.

## القسم ٢٩ — سياسة انتهاء البرنامج

- البرامج المنتهية تبقى ظاهرة بحالة **Completed**. من أكمل وحصل على شهادة يظهر البرنامج Completed في لوحته. لا تُخفى الحقيقة إلا لسبب قانوني/جودة.

## القسم ٣٠ — سياسة الاسترداد والانسحاب

- **لا انسحاب ذاتي ولا زر انسحاب عام.** المتدرّب يتواصل مع الإدارة.
- الأدمن يقدر: إسناد/إزالة برنامج · إلغاء تسجيل · تأكيد دفع · تعديل حالة — كله بسجل تدقيق.
- الاسترداد يتطلّب Finance Admin أو Super Admin؛ الأفعال المالية الحسّاسة تستخدم Four-Eyes عند الإمكان.

## القسم ٣١ — سياسة حوكمة الأدمن

- كل شيء يُدار من الأدمن: إنشاء · حالة · ظهور · نشر · أرشفة · إسناد · تتبّع · تقارير.
- كل مورد أدمن يدعم: بحث · رقم مرجع · حالة · نطاق تاريخ · تصدير عند السماح · سجل تدقيق · فلترة بالمالك/الكيان.

## القسم ٣٢ — سياسة البحث

- السجلّات المهمة قابلة للبحث بـ: اسم · مرجع تجاري · بريد · جوال · حالة · نطاق تاريخ.
- البحث العام يغطّي: برامج/مسارات/مختبرات/مبادرات. بحث الأدمن يغطّي كل الكيانات التشغيلية.

## القسم ٣٣ — سياسة التقارير

- تقارير الأدمن تغطّي: برامج · تسجيلات · استشارات · شهادات · دفعات · حضور · مراجعات · مستخدمون · مدربون.
- التصدير حسب الدور: المدرب (متدربوه المسندون فقط) · Finance (المالي المخوّل فقط) · Super Admin (الكل). كل تصدير حسّاس مُدقّق.

## القسم ٣٤ — سياسة النسخ والاستعادة

- نسخ قاعدة البيانات: **يومي**. نسخ المنصّة الكامل: **أسبوعي**. الاحتفاظ: يومي 30 يوم · أسبوعي 12 أسبوع · شهري 12 شهر.
- نسخة **خارج الخادم** إلزامية. تمرين استعادة كل **3 أشهر** على الأقل. فشل النسخ يُطلق تنبيهاً.

## القسم ٣٥ — سياسة الأمن والجلسات

- جلسات آمنة · rate limits · صلاحيات قائمة على الأدوار · **2FA لـ Super Admin/Admin** حيث ينطبق · تسجيل الأفعال الإدارية الحسّاسة.
- لا تُكشف الأسرار · لا تُكشف DB IDs · لا تُكشف التفاصيل المالية لأدوار غير مخوّلة.
- **انتحال الأدمن (Impersonation)** يتطلّب: إذن Super Admin · سبب · سجل تدقيق · مؤشّر جلسة واضح.

## القسم ٣٦ — سياسة Feature Flags

- الميزات المستقبلية الكبرى **قابلة للتفعيل/التعطيل** بأمان دون كسر المنصّة. أمثلة: AI · Community · تطبيق جوال · Gamification · تحليلات متقدّمة · مراجعات عامة · معرض · صفحات شركاء.

## القسم ٣٧ — سياسة الذكاء الاصطناعي

- وحدة AI كقدرة مستقبلية، **الافتراضي معطّل**. قد تدعم: مساعد متدرّب/مدرّب · صياغة وصف برنامج · تلخيص واجبات · تحليل مراجعات · اقتراح محتوى.
- **AI لا يجوز له:** إصدار شهادات · اعتماد حضور · اعتماد إكمال · قرارات مالية · قرارات أكاديمية نهائية. **القرار البشري نهائي**، ومخرجات AI تُراجَع قبل النشر.

## القسم ٣٨ — سياسة استقلال المورّدين

- المزوّدون الخارجيون **قابلون للاستبدال** عبر تجريد (abstraction): Tap · Tabby · Tamara · Apple Pay · Resend · Calendly · Drive · OneDrive · مزوّدو الفيديو · مزوّدو SMS. لا تنهار أي عملية جوهرية باستبدال مورّد واحد.

## القسم ٣٩ — الصفحات القانونية والعامة

- تُدار من الأدمن (لا hardcode): سياسة الخصوصية · شروط الاستخدام · سياسة الاسترداد · سياسة الشهادات · سياسة الحضور · سياسة رفع المحتوى · سياسة المراجعات. كل صفحة تدعم **الإصدارات وتاريخ النشر**.

## القسم ٤٠ — بوّابات الجودة (Quality Gates)

قبل نشر أي كيان تعليمي عام، تُتحقّق الحقول المطلوبة:
- **برنامج:** عنوان · وصف · صورة · تواريخ/توفّر · نمط حضور · مدينة (إن حضوري) · مدربون · سعر (إن مدفوع) · حالة · إعدادات تسجيل · إعداد شهادة · نموذج إكمال.
- **مسار:** عنوان · وصف · برامج مضمّنة · سعر · حالة · إعدادات تسجيل.
- **استشارة:** محتوى الصفحة · نموذج الطلب · سير عمل الأدمن · تفعيل التتبّع.
- **لا محتوى عام ناقص.**

## القسم ٤١ — القاعدة الرئيسية (Master Rule)

أي ميزة **غير مكتملة** إن نقصها: مرجع تجاري · إدارة من الأدمن · دورة حالة · سجل تدقيق · ملكية · قابلية بحث · ضوابط ظهور · صلاحيات أدوار · وضوح للمستخدم عند الحاجة. إن عجزت ميزة عن تحقيق هذه — لا تُعتبر جاهزة.

# الملحق (أ) — تحليل الفجوات (مبنيّ على فحص الكود الفعلي 2026-06-09)

> الأدلّة من فحص فعلي للمستودع. ما لم يُفحص بعمق مُعلَّم بـ «يحتاج تأكيد».

## أ-١. تعارضات مع التنفيذ الحالي
1. **المراجع التجارية:** لا يوجد نظام موحّد. فقط `ConsultationRequestModel` يولّد `WMT-C-XXXXXX` (**لاحقة عشوائية**، لا تسلسل شهري `WMT-C-2606-0001`). التحقّق من الشهادة يستخدم **UUID خام** في الرابط — يخالف القسمين ٣ و١٤.
2. **مُعرّفات DB مكشوفة:** صفحات المدربين تستخدم UUID في المسار (`/instructors/{uuid}`)، والتحقّق `verify/{uuid}` — يخالف القسم ٣.
3. **تسميات الأدوار:** الموجود `instructor` (لا `Trainer`)، `student` (لا `Learner`)، `academy_owner` (≈ Super Admin)، `finance` (≈ Finance Admin) — تعارض تسميات مع القسم ٢.
4. **كيانات غير منمذجة ككيانات مستقلة:** لا يوجد موديل `LearningPath` ولا `TrainingLab` ولا `Initiative` — يخالف الأقسام ١٠/١٢/١٣ (يُرجّح أنها حالياً برامج أو غير موجودة — يحتاج تأكيد لحقل نوع في `ProgramModel`).
5. **الاستشارات بلا soft-delete:** `ConsultationRequestModel` **لا يستخدم SoftDeletes** — يخالف القسم ٢٨ (طلبات الاستشارة لا تُحذف نهائياً).

## أ-٢. حقول قاعدة بيانات ناقصة
- **مرجع تجاري** (`business_reference`/`reference_number`) على: users · enrollments · payments(orders) · invoices · certificates · programs · paths · labs · initiatives · tickets. (موجود فقط ضمنياً على الاستشارة كـ tracking.)
- **عدّاد تسلسل شهري/سنوي** (جدول/خدمة) لتوليد المراجع — غير موجود.
- أعمدة `email_verified_at`/`phone_verified_at` موجودة لكن **غير مستخدمة** (القسم ٢٥ — مقبول مؤجّلاً).
- soft-delete مفقود على: ConsultationRequest · (يحتاج تأكيد) Enrollment · AttendanceRecord — القسم ٢٨.

## أ-٣. موارد أدمن (Filament) ناقصة
الموجود (٢٤ مورد): Program · Category · Lesson · Media · Quiz · Assignment · CohortBatch · LiveSession · Order · Invoice · Coupon · Review · Partner · ContactMessage · **ConsultationRequest (جديد)** · FailedJob · EmailOutbox · PaymentWebhook · TenantAuditLog · Tenant · SystemUser · AuditLog · Plan.
**ناقص موارد لـ:** Learning Path · Training Lab · Initiative · Gallery/Success Stories · Trainer (إدارة مدربين مخصّصة) · Team Members · Certificate (المُصدرة) · Enrollment · Attendance · Support Ticket · Users/Learners (إدارة المستخدمين التشغيلية). يخالف القسم ٣١.

## أ-٤. سجلّات تدقيق ناقصة
`AuditAction` شامل لكنه **يفتقد**: `EmailChanged` · `MobileChanged` · `PermissionChanged` (موجود role لا permission) · `CertificateRevoked` · `ConsultationApproved`/`ConsultationRejected` · `AttendanceChanged` · `CompletionApproved` · `AdminImpersonation` · `FileAccessed (sensitive)` · `RefundProcessed` (موجود `OrderRefunded` ~). يخالف القسم ٥.

## أ-٥. صلاحيات/أدوار ناقصة
- **أدوار ناقصة:** `Consultant` · `Team Member` (القسم ٢). الموجود: academy_owner/admin/instructor/cohort_lead/marketing/finance/support/affiliate/student.
- **الجدار المالي (القسم ٧):** يحتاج تأكيد أن المدرب فعلاً محجوب عن البيانات المالية في الموارد، وأن مبدأ Four-Eyes غير منفّذ (يُرجّح غير موجود).
- **Impersonation محكوم** (القسم ٣٥): يحتاج تأكيد وجوده.

## أ-٦. إصلاحات فورية (منخفضة المخاطر، عند الاعتماد)
1. توحيد **نظام المراجع التجارية** + خدمة توليد تسلسلية (يحلّ أ-١.١، أ-٢).
2. إضافة الأدوار الناقصة: **Consultant · Team Member**.
3. إضافة سجلّات التدقيق الناقصة (enum cases) — رخيص.
4. تفعيل **SoftDeletes** على الاستشارات (+ تأكيد Enrollment/Attendance).
5. **Feature-flag** بسيط (config-driven) للميزات المؤجّلة (Community/AI/Gallery) — القسمان ٣٦/٣٧.

## أ-٧. إصلاحات مؤجّلة (تتبع إطلاق التدفّقات)
- تحقّق البريد (لين يجهز Resend) · OTP الجوال (لين يوجد مبرر) · Calendly/الدفع للاستشارات · سوق المستشارين · المجتمع · AI · صفحات قانونية مُدارة بإصدارات · Four-Eyes للأفعال المالية · بوّابات الجودة الكاملة للنشر.

## أ-٨. ترتيب التنفيذ الموصى به
1. **الأساس الحاكم:** نظام المراجع التجارية + الأدوار الناقصة + سجلّات التدقيق الناقصة + soft-delete الحرجة. *(يجعل كل ما بعده ممتثلاً)*
2. **نمذجة الكيانات الأربعة بوضوح** (Path/Lab/Initiative ككيانات أو أنواع برنامج محسومة) + موارد أدمنها.
3. **الجدار المالي + Four-Eyes** عند تفعيل الدفع.
4. **بوّابات الجودة للنشر** (القسم ٤٠) قبل فتح النشر العام الموسّع.
5. **المؤجّلات** (بريد/OTP/Calendly/AI/Community) خلف feature-flags حسب الحاجة الفعلية.
