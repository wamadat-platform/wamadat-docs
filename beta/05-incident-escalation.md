# مسار تصعيد الحوادث الحرجة

> **متى تفتح هذا الملفّ**: لحظة ما يحدث شيء غير عادي — مستخدم بيتا أبلغ عن مشكلة، Sentry فيه issue جديد، daily summary أحمر، أو حدسك يقول "في شي مش طبيعي".
> **الهدف**: قرار سريع وموثَّق بين 4 مسارات: إصلاح فوري، rollback، تخفيف مؤقّت، أو تأجيل.

---

## مستويات الخطورة (Severity)

| المستوى | التعريف | مهلة الاستجابة المستهدفة | أمثلة |
|---|---|---|---|
| **P0 — حرج** | المنصّة down، أو data loss، أو فقدان بيانات مستخدم، أو ثغرة أمنية مفتوحة | **≤2 ساعة** قرار + بداية تنفيذ | `/up` يرجع 500، DB لا يستجيب، payment webhook يكتب على tenant خطأ، حساب admin مفتوح للجميع |
| **P1 — مهم** | ميزة جوهرية مكسورة لكلّ المستخدمين | **≤24 ساعة** | sign-up يفشل، checkout لا يوصل، lessons لا تفتح، Sentry يلتقط نفس الخطأ من 3 مستخدمين |
| **P2 — متوسّط** | ميزة جوهرية مكسورة لمستخدم واحد، أو ميزة هامشية مكسورة للجميع | **≤7 أيام** | مستخدم واحد يقول "ما قدر ينزّل شهادة" والباقي يقدرون، تصميم mobile متشوّش |
| **P3 — منخفض** | تحسين، تصحيح إملائي، اقتراح | **≤30 يوم** أو backlog | typo في صفحة، اقتراح ميزة جديدة |

---

## شجرة القرار (P0 / P1)

```
هل المنصّة كاملة down (/up يرجع ≥ 500)?
├─ نعم →  إجراء فوري:
│         1. افتح `docs/operations/02-rollback.md`
│         2. نفّذ rollback لآخر commit أخضر (آخر تاج deploy)
│         3. ابعث رسالة للـ cohort: "نواجه مشكلة، نعمل عليها — تحديث خلال X دقيقة"
│         4. بعد الاستقرار، افحص السبب (Sentry + laravel.log) قبل push جديد
│
└─ لا → استمرّ في الفحص:

   هل المشكلة في DB / Backup / Restore?
   ├─ نعم → افتح `docs/operations/03-db-recovery.md`
   │
   └─ لا → استمرّ:

      هل Queue worker متوقّف?
      ├─ نعم → افتح `docs/operations/04-worker-supervision.md`
      │
      └─ لا → استمرّ:

         هل الخطأ يلتقطه Sentry لمستخدم محدّد فقط?
         ├─ نعم → اتصل بالمستخدم مباشرة عبر WhatsApp:
         │         "لاحظت خطأ في حسابك، تقدر تشرح لي ايش كنت تسوّي؟"
         │         اجمع: المتصفح، الوقت، الـ flow، الـ screenshot
         │         افتح Sentry → ابحث عن نفس الـ event ID → نفّذ patch خصوصي
         │
         └─ لا (الخطأ عام) → P1 — patch خلال 24h ساعة، عبر:
                  1. أنشئ branch جديد من main
                  2. اكتب الـ fix + اختبار يثبت الخطأ + يثبت الإصلاح
                  3. push → احرص CI يمرّ
                  4. merge → deploy
                  5. أرسل تحديث للـ cohort: "تم إصلاح المشكلة، شكراً للإبلاغ"
```

## قرار rollback مقابل forward fix

| الحالة | اختر | لماذا |
|---|---|---|
| المنصّة down + سبب مرتبط بـ deploy حديث (≤24 ساعة) | **Rollback** | السبب معروف، الـ fix يحتاج وقت، الـ users ينتظرون |
| المنصّة down + سبب غير معروف | **Rollback** ثم تشخيص | الـ rollback يعيد الخدمة، التشخيص يصير في "مع وقت" |
| ميزة واحدة مكسورة + المنصّة شغّالة | **Forward fix** + اتصال بالمتأثّر | rollback يفقد ميزات أخرى |
| Sentry issue من مستخدم واحد، الباقون يشتغلون | **Investigate + forward fix** | rollback مكلف وغير ضروري |
| Schema migration حديث سبّب الكسر | **Rollback أو migration revert** | مشاورة `03-db-recovery.md` |

## قوالب التواصل مع الـ cohort (عربي)

### قالب 1 — إعلان incident فوري (لما المنصّة down)

```
السلام عليكم،
لاحظنا الآن مشكلة تقنيّة في ومضات. نشتغل عليها.
أتوقّع التحديث خلال 30 دقيقة.
آسف على الإزعاج. — مشعل
```

(أرسل في WhatsApp/Telegram لكلّ مدعوّ. لا تنشر علناً.)

### قالب 2 — إعلان الحلّ

```
تم الإصلاح ✅
السبب: {شرح بسيط بكلمتين، بدون مصطلحات تقنيّة}
المدّة الكاملة للانقطاع: X دقيقة
شكراً لصبركم. — مشعل
```

### قالب 3 — رسالة استفسار خاصّة (مشكلة على مستخدم واحد)

```
يا {اسم}، لاحظت في النظام إشارة لخطأ حصل عندك قبل قليل.
تقدر تذكر إيش كنت تسوّي؟ (أيّ صفحة، أيّ زر، الوقت)
أحتاج معلومتك علشان أصلح قبل ما يصير لأحد آخر.
— مشعل
```

### قالب 4 — رسالة شكر على blocker reported

```
{اسم}، تنبيهك أنقذنا.
الخطأ كان P{0/1} وكان حيوصل لأشخاص ثانيين لو ما حدّدته.
صلّحته الآن. ابعتلك تحديث خلال ساعة.
— مشعل
```

## ما يجب توثيقه بعد كلّ P0 / P1

أنشئ سطر جديد في `docs/operations/incidents-log.md` (أنشئ الملفّ لو ما موجود):

```markdown
## YYYY-MM-DD HH:MM — P{0/1} — {عنوان مختصر}

**اكتُشف عبر**: {Sentry / daily summary / user report / حدس}
**التأثير**: {كم مستخدم تأثّر، كم مدّة الانقطاع}
**السبب الجذري**: {سطر واحد}
**الحلّ**: {forward fix commit SHA / rollback إلى commit SHA}
**ما تعلّمته**: {سطر — يدخل في `docs/beta/04-daily-monitoring-checklist.md` لو يستحقّ check جديد}
```

## ما لا تفعل في الـ incident

- ❌ **لا تَلُمّ المستخدم** — حتى لو كان "userError"، هذه تجربتك أن تجعل المنصّة تتحمّل الأخطاء البشريّة
- ❌ **لا تَكتم الـ incident** — لو شخص متأثّر، يستحقّ تحديث صريح
- ❌ **لا تُصلح في الإنتاج مباشرة بـ SSH** — كلّ تعديل يمرّ بـ git + CI (للحفاظ على restore-drill validity)
- ❌ **لا تأخذ قرار rollback بدون قراءة `02-rollback.md` كاملاً** — `git reset --hard` على main عملية مدمّرة
- ❌ **لا تتجاهل P0 ليلاً** — لو احتجت تنام، اعمل خطوة `php artisan down` (down mode) قبل النوم، ارفعها الصباح. صفر تجربة سيّئة > تجربة سيّئة دائمة

---

## إذا الحدث P0 وأنت غير قادر تستجيب

- يحدث (سفر، مرض، طوارئ شخصيّة)
- نفّذ هذه الخطوة **قبل** الانقطاع المعروف عن المراقبة:
  ```powershell
  cd C:\Users\U\wamadat-platform\backend
  php artisan down --message="نقوم بصيانة سريعة — نعود خلال X ساعة"
  ```
- أرسل رسالة جماعيّة بـ WhatsApp: "ومضات في صيانة ربع ساعة — رسالة جديدة لما ترجع"
- لمّا ترجع: `php artisan up`
- صيانة مخطّطة = تجربة مستخدم مقبولة. صمت + كسر = تجربة سيّئة.
